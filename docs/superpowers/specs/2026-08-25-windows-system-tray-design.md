# Windows 系统托盘状态设计

## 背景

下载器后台由隐藏的 PowerShell supervisor 和 Python service 运行。配置器关闭后，后台下载继续，但 Windows 任务栏通知区域没有常驻图标。用户只能重新打开配置器、查看任务管理器或读取心跳文件，才能判断后台是否运行。

本功能为现有 Tk 配置器增加系统托盘入口，让后台状态、下载进度和常用操作始终可见，同时保持下载服务与图形界面相互独立。

## 目标

- 点击配置器右上角“×”时隐藏到系统托盘，不停止后台下载。
- 使用颜色区分正常运行、启动或心跳异常、配置或登录错误、已停止。
- 鼠标悬停可查看当前文件、百分比和速度；无当前文件时显示队列摘要。
- 托盘菜单可打开配置器、启动或停止后台、打开下载目录、打开日志目录，以及退出托盘。
- 后台停止后保留灰色图标，可从托盘重新启动。
- 重复双击配置器只唤醒已有窗口，不产生多个窗口或托盘图标。
- 托盘功能不改变 Telegram 登录、群组白名单、下载队列、断点续传和 supervisor 行为。

## 非目标

- 不增加 Windows 开机启动、计划任务或系统服务。
- 不把托盘代码放入下载 service，也不让托盘直接连接 Telegram。
- 不增加独立的进度弹窗；完整详情继续在配置器“运行”页展示。
- 不在正常下载过程中持续发送系统通知。

## 方案选择

采用“配置器与托盘合一”：Tk 配置器和托盘图标属于同一个 `pythonw.exe` 进程，下载 service 继续由现有 supervisor 独立管理。

未采用独立托盘进程，因为它需要额外的进程生命周期、通信和重复实例管理。未把托盘嵌入下载 service，因为 service 会被 supervisor 重启，且界面职责会与下载职责耦合。

## 架构

### TrayController

新增独立托盘控制模块。它封装 `pystray` 和 Pillow，负责：

- 在辅助线程启动和停止 Windows 托盘图标。
- 在内存中生成圆形下载箭头图标，不创建外部图片文件。
- 根据不可变状态快照更新图标颜色、悬停文字和菜单可用性。
- 把菜单回调调度回 Tk 主线程；托盘线程不直接调用 Tk 控件。
- 捕获托盘后端异常并把安全、无敏感信息的错误交回配置器展示。

`DownloaderApp` 仍通过现有 `_refresh_status` 每 2 秒调用一次 `GuiController.read_status()`。同一份快照同时更新“运行”页和 `TrayController`，避免出现两套心跳判断逻辑。

### 窗口生命周期

配置器启动并成功建立托盘后，`WM_DELETE_WINDOW` 改为隐藏窗口：

1. 调用 `withdraw()` 隐藏 Tk 根窗口。
2. 保持 Tk 事件循环、状态刷新、异步桥和托盘线程运行。
3. 双击托盘图标或选择“打开配置器”时调用 `deiconify()`、`lift()` 并请求焦点。

如果托盘初始化失败，“×”保持原有的关闭界面行为，并先显示错误，避免窗口隐藏后无法恢复。

托盘“退出托盘”执行真正的界面退出：停止托盘线程、取消 Tk 回调、关闭异步桥、销毁根窗口并释放 GUI 单实例锁。该操作不得调用 `GuiController.stop()`，也不得创建 `stop.flag`，因此后台下载继续运行。

### GUI 单实例与唤醒

在 `.runtime` 中增加两个仅限项目内的控制文件：

- `gui.lock`：使用现有 Windows 字节锁模式，在配置器完整生命周期内持有。
- `gui-activate.request`：重复启动时写入新的随机请求令牌。

首个实例持有 `gui.lock` 并定期读取激活请求令牌。第二个实例获取锁失败时，不显示错误窗口，而是写入新的激活令牌并立即退出。首个实例发现令牌变化后恢复并置顶窗口。请求文件可保留最后一个令牌；它不含账号、路径以外的数据或 Telegram 信息。

锁和激活请求路径作为 `ProjectPaths` 的明确字段管理，并继续受 `assert_within_root` 约束。异常退出后锁由操作系统释放，残留文件不会阻止下一次启动。

## 状态呈现

状态映射如下：

| 心跳状态 | 图标 | 含义 | 菜单操作 |
| --- | --- | --- | --- |
| `running` | 绿色 | 后台心跳正常 | 可停止，不可重复启动 |
| `starting` | 黄色 | 启动请求已发送，等待心跳 | 可停止，不可重复启动 |
| `stale` | 黄色 | 最后报告运行，但超过 15 秒无心跳 | 可停止，不可重复启动 |
| `needs_login` | 红色 | Telegram 会话失效 | 可打开配置器、停止后台 |
| `needs_config` | 红色 | 配置或目标无效 | 可打开配置器、停止后台 |
| `error` | 红色 | 后台发生未处理错误 | 可打开配置器、停止后台 |
| `stopped` 或无心跳 | 灰色 | 后台未运行 | 可启动，不可停止 |

启动动作成功发出后，配置器和托盘立即进入 `starting`，随后由真实心跳覆盖。停止动作写入现有 `stop.flag`；图标在服务心跳确认停止前保持当前或过渡状态，不伪造已停止结果。

## 悬停文字与菜单

Windows 托盘标题保持简短并限制长度：

- 有下载进度：`正在下载｜<截断文件名>｜67.0%｜211 KiB/s`
- 正常运行但无当前文件：`后台正常｜等待 777｜已完成 11`
- 异常：`心跳异常｜请打开配置器检查`
- 停止：`后台已停止｜右键可启动`

格式化逻辑是无 UI 依赖的纯函数。缺失、类型错误、非有限数值或超长文件名必须降级为安全占位文本，不能导致托盘线程退出。

右键菜单顺序：

1. 不可点击的当前状态摘要。
2. 打开配置器（默认动作，双击图标也执行）。
3. 启动后台或停止后台，按当前状态启用其中一个。
4. 打开下载目录。
5. 打开日志目录。
6. 退出托盘。

## 错误处理

- 托盘初始化失败：配置器保持可见，显示脱敏错误，并保留原有关闭行为。
- 状态读取失败：托盘显示红色和安全错误摘要；下一次刷新继续重试。
- 启动、停止或打开目录失败：通过托盘通知和配置器错误框报告；托盘继续运行。
- Tk 已开始退出时到达的托盘回调应被忽略，不再访问已销毁控件。
- 退出流程必须幂等；无论从窗口回退关闭还是托盘退出触发，都只清理一次。
- `pystray`、Pillow 和 Windows 托盘后端加入自检。依赖缺失只影响界面可见性，不得修改下载状态。

## 依赖与数据位置

`pystray` 和 Pillow 作为项目运行依赖安装到项目 `.venv`。pip 缓存、临时文件和字节码继续由现有启动脚本定向到项目 `.cache` 与 `.tmp`。图标只在内存中生成，不写入用户目录、系统临时目录或 C 盘项目数据目录。

新增运行文件仅为 `.runtime/gui.lock` 和 `.runtime/gui-activate.request`。它们不包含凭据、会话、二维码令牌、手机号或下载内容。

## 测试策略

### 单元测试

- 每个心跳状态映射到正确颜色、悬停文字和菜单启停状态。
- 下载文件名、百分比、速度和队列摘要格式正确，并能容忍缺失或畸形数据。
- 窗口“×”在托盘可用时隐藏，在托盘不可用时不隐藏。
- 托盘恢复动作显示并置顶窗口。
- 托盘退出清理 GUI，但不调用后台停止动作。
- 托盘菜单的启动、停止、打开下载目录和打开日志目录调用正确控制器方法。
- 托盘线程回调只通过 Tk 调度器进入主线程。
- 重复启动写入激活请求，首个实例响应请求；残留请求文件和已释放锁不阻止正常启动。
- 退出和迟到回调是幂等且安全的。

测试使用伪造托盘后端和伪造 Tk 对象，不依赖真实鼠标、Explorer 或通知区域。

### 集成与回归测试

- 自检覆盖托盘依赖和后端可用性。
- PowerShell 启动脚本仍不创建计划任务、不写项目外数据、不隐藏交互窗口。
- 运行完整 pytest 和 compileall，确保下载、登录、队列、诊断与 Windows supervisor 回归测试全部通过。

### Windows 冒烟验收

1. 在后台已运行和已停止两种状态下分别启动配置器。
2. 点击“×”，确认窗口隐藏且托盘图标保留。
3. 确认颜色、悬停文件名、百分比和速度与“运行”页心跳一致。
4. 从托盘打开下载目录，再恢复配置器。
5. 重复双击启动入口，确认只恢复已有窗口且没有第二个托盘图标。
6. 从托盘停止并重新启动后台，确认状态按真实心跳变化。
7. 选择“退出托盘”，确认 GUI 进程退出而下载 service 仍然存活并持续更新心跳。
