# 在线更新锁检测修复设计

## 背景与目标

`SingleInstance` 在 Windows 上使用 `msvcrt.locking` 对锁文件的第一个字节加非阻塞排他锁。现有 `_file_is_locked()` 只尝试再次打开文件；Windows 允许其他进程打开带有字节范围锁的文件，因此后台真实运行时 `downloader_is_running()` 仍可能返回 `False`。

在线更新安装流程依赖该结果决定是否先停止后台以及更新后是否恢复后台。本次修复必须让状态探测与单实例锁采用相同机制，避免更新期间后台继续运行，同时不改变下载、队列、心跳或选择性下载行为。

本次修复发布版本为 `v0.3.1`。

## 方案选择

采用真实字节锁探测：在 Windows 上以可读写方式打开已有锁文件，对第一个字节尝试 `LK_NBLCK`。探测失败表示其他进程持有锁；探测成功表示当前未被占用，并立即释放探测锁。

不采用以下方案：

- 心跳 PID：心跳可能陈旧，无法作为更新停服的唯一依据。
- Windows 命名互斥量：需要迁移现有单实例机制，超出补丁范围。

## 行为与边界

- 锁文件不存在时返回未运行，不创建文件。
- 文件存在且可成功获取同一字节锁时返回未运行，并在返回前释放锁。
- 获取字节锁失败或文件因共享模式无法打开时返回运行中。
- 非 Windows 平台保持原有保守打开检查，项目正式运行目标仍为 Windows。
- 探测只持锁极短时间，不写入、截断或删除锁文件。
- `SingleInstance` 的加锁、PID 写入和释放行为保持不变。
- 在线更新继续通过现有 `restore_service` 流程停服、等待并在更新后按原状态恢复。

## 错误处理与竞态

探测成功后的解锁放在 `finally` 路径；即使显式解锁异常，关闭句柄也会释放本进程的临时锁。锁文件在存在检查与打开之间消失时按未运行处理。权限或共享冲突表示当前不能安全证明后台已停止，因此按运行中处理。

状态探测只是瞬时判断，真正的单实例安全仍由服务启动时的 `SingleInstance` 保证。本补丁不增加轮询、常驻线程或后台开销。

## 测试与验收

- 使用真实 `SingleInstance` 占用 `downloader.lock`，确认修复前回归测试失败、修复后 `downloader_is_running()` 返回 `True`。
- 退出锁上下文后确认返回 `False`。
- 只有遗留锁文件但无人持锁时确认返回 `False`。
- 保留 GUI 更新控制器关于运行中停服、停止超时和恢复状态的既有测试。
- 运行完整 `scripts/check.ps1`、`pip check`、`compileall` 和工作区检查。
- 在真实后台保持运行时执行只读锁探测，确认识别为运行中且心跳继续推进；不在验收中实际安装更新或停止当前下载。
- 将包版本提升到 `0.3.1`，更新 README/验证记录，快进合并到 `master`，并向 GitHub、魔塔推送同一提交及带说明的 `v0.3.1` 标签。

## 非目标

- 不修改 Telegram 自检在后台占用会话时产生的 `database is locked` 警告。
- 不调整选择性下载、任务优先级、下载目录或进度条。
- 不重写远端 `v0.3.0` 标签，也不把更新机制改为自动检查。
