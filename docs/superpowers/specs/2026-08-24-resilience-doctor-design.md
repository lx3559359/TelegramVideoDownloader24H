# Telegram 下载器可靠性与一键自检设计

## 背景与目标

现有版本已经具备严格群组白名单、首次历史扫描、实时下载、任务持久化、原子文件落盘、项目内数据隔离和 Windows 后台守护。下一版在不改变这些边界的前提下，解决短暂断网和群组重新启用时的增量补抓缺口，并提供普通用户可理解的一键自检。

成功标准：

- 只访问配置中明确选择的群组，不增加全选或账号全量监听。
- 服务启动、短暂断网恢复、群组移除后重新启用三种场景都能按消息游标补抓遗漏视频。
- 群组访问失败不会每秒请求 Telegram，而是按群独立退避。
- GUI 能识别陈旧心跳，展示启动错误、配置错误、永久失败数和当前任务。
- GUI 提供“一键自检”，诊断报告经过脱敏并保存在项目内 `logs/diagnostics/`。
- 不创建 Windows 服务、计划任务、启动项或项目外目录，不向 C 盘写入项目数据。

## 方案选择

### 方案 A：集成式可靠性修复与自检（采用）

在现有 Python 服务和 Tkinter GUI 内增加周期补抓、访问退避、可信状态和诊断模块。沿用当前进程模型和 SQLite 队列，改动集中，能够直接覆盖用户最关心的长期运行问题。

### 方案 B：只增加 PowerShell 自检脚本

实现成本较低，但普通用户不易发现，无法解决断线漏抓、陈旧心跳和 GUI 错误信息缺失，因此不采用。

### 方案 C：改造成 Windows 服务并加入系统级监控

系统重启后恢复能力更强，但会产生系统级配置并可能占用 C 盘，与项目数据隔离和“不创建计划任务”的既定边界冲突，因此不采用。

## 组件设计

### 1. 增量补抓

`ScannerCoordinator` 保留实时事件处理和历史扫描，新增周期补抓循环：

- 服务注册事件处理器后，先对所有已启用群执行一次 `catch_up_once`。
- 运行期间每 5 分钟对已启用群执行一次增量补抓。
- 配置热更新发现一个曾经存在但被禁用的群重新启用时，立即执行增量补抓。
- 新首次加入的群仍以“记录当前最新消息 ID + 从当前向历史扫描”的方式覆盖全部历史，避免重复的前向补抓。
- 增量任务继续使用 `catchup` 来源和实时优先级，数据库主键保证重复消息不会重复下载。

### 2. 群组访问退避

协调器为每个群维护进程内失败次数和下次允许访问时间。群访问失败后的退避依次为 1 分钟、5 分钟、30 分钟，此后保持 30 分钟；任意一次成功访问会清零。退避同时作用于历史扫描和周期补抓，但不影响其他群组。

退避状态不写入新的系统位置。服务重启后退避从头开始，持久任务和消息游标仍由 SQLite 保留。

### 3. 可信运行状态

服务在读取配置和凭据前就初始化心跳与无敏感信息日志：

- 缺少或无效配置写入 `needs_config`。
- 会话失效写入 `needs_login`。
- 未处理异常写入 `error`。
- 正常运行每 5 秒更新心跳。

GUI 读取心跳时，如果 `running` 心跳超过 15 秒没有更新，则显示 `stale`，并保留原始状态和错误说明。GUI 同时展示 `error`、`config_error`、`permanent_error` 和当前任务文件名。

下载工作器只暴露当前任务的安全显示名称，不把 API Hash、手机号、验证码、密码或 Telegram 会话内容写入心跳。

### 4. 一键自检

新增独立 `diagnostics.py`，返回结构化检查结果，每项状态为 `pass`、`warning` 或 `fail`。本地检查包括：

- 项目根目录及五个运行目录都位于项目内并可写。
- Python 版本、Telethon 版本和核心包可导入。
- 配置、凭据格式和非空白名单；报告只记录“存在/有效”，不记录值。
- 下载盘剩余空间是否高于 512 MiB 安全余量。
- SQLite 存在时执行 `PRAGMA quick_check`。
- 心跳 JSON、更新时间、后台状态和停止标记是否一致。

在线检查通过现有 Telegram 网关执行：连接、会话授权、列出当前账号可见群组，并确认每个白名单群仍可见。在线检查不发送验证码、不修改账号、不下载媒体。

GUI“运行”页新增“运行自检”按钮。检查在线程桥中执行，完成后弹出摘要并把完整 JSON 报告原子保存为 `logs/diagnostics/doctor-<UTC时间>.json`。报告中的异常文本使用与日志相同的敏感值替换规则。

### 5. 命令行与兼容性

命令行增加 `doctor` 子命令，便于无 GUI 排障。默认执行本地检查；存在有效凭据与会话时继续在线检查。返回码规则：全部通过为 0，存在警告但无失败为 1，存在失败为 2。

现有 `gui`、`service` 命令和双击启动方式保持不变。数据库结构本轮不新增列，不需要迁移。

## 错误处理与安全

- 自检中的单项异常转换成该项失败，不中断后续检查。
- Telegram 网络错误显示为在线检查警告或失败，不改变配置、会话、群组选择和下载队列。
- 报告只保存诊断摘要、版本、布尔状态、计数和脱敏错误；不保存凭据内容、验证码、密码或会话文件内容。
- 所有新文件通过 `ProjectPaths` 解析，并在写入前执行项目根路径断言。

## 测试策略

按测试驱动开发实施：

- 协调器测试覆盖周期补抓、重新启用补抓、禁用群不访问、访问错误退避和成功后清零。
- 服务测试覆盖 `needs_config`、周期补抓任务生命周期、当前任务心跳和既有停止语义。
- 控制器与 GUI 测试覆盖陈旧心跳、错误字段、永久失败数和自检按钮调用。
- 诊断模块测试覆盖路径、磁盘、配置、SQLite、心跳、脱敏报告和在线白名单校验。
- Windows 脚本测试继续保证临时目录、缓存、虚拟环境和所有报告都留在项目根目录。
- 完整 `scripts/check.ps1` 必须通过，且不降低现有 44 项测试的白名单、恢复和路径隔离保证。

## 明确不包含

- Windows 服务、计划任务、开机启动或系统托盘。
- 多账号、代理配置、下载限速、并行下载或 Web 管理界面。
- 自动修复配置、自动重新登录、自动重新加入群组。
- 将诊断报告上传到任何外部服务。
