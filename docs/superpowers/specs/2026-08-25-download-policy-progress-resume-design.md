# Telegram 下载策略、进度与断点续传设计

日期：2026-08-25  
状态：已获用户口头批准，等待书面规格复核

## 1. 背景与结论

用户反馈点击启动后台后仍看不到视频进入下载目录。现场诊断确认：

- 服务处于 `running`，已扫描并排队 788 个历史视频。
- 当前 317,192,825 字节的视频已经持续发送 `GetFileRequest`，并非没有开始下载。
- 下载实现没有把字节进度写入心跳或 GUI；打开的 `.part` 文件在完成前也无法提供可靠的可见进度，因此用户看到完成数为 0、下载目录为空。
- 项目虚拟环境没有安装 `cryptg`，Telethon 使用纯 Python AES-IGE，256 KiB 数据块处理缓慢。
- 当前实现会在服务重启时删除 `.part`，大文件只能从头开始；多次诊断重启因此丢失了已有传输进度。

本次改动采用以下组合方案：

1. 每个群组或频道单独配置是否下载历史视频。
2. 暂停历史下载时保留队列和扫描游标，不删除任务。
3. 新内容监听始终有效，不受历史开关影响。
4. 增加真实字节进度、速度、断点续传、停滞重试和可取消停止。
5. 在项目 `.venv` 中安装并声明 `cryptg` 加速依赖。

> 核心原则：历史任务可以暂停和恢复，新内容始终监听；任何中断都尽量保留已下载字节。

## 2. 目标与非目标

### 2.1 目标

- GUI 可为每个已选群组或频道独立开启“下载历史”。
- 关闭历史下载后，已有历史任务不再被领取，但实时和断线补抓任务继续运行。
- 重新开启后从原队列和扫描游标继续。
- GUI 显示当前文件的已下载大小、总大小、百分比和平均速度。
- `.part` 文件在项目 `.tmp` 中持续增长，异常退出后可从安全断点续传。
- 120 秒没有任何下载进度时自动取消本次请求并进入现有重试策略。
- 停止后台时及时取消下载请求并保留安全断点。
- 所有缓存、日志、会话、数据库、临时文件和下载结果继续限制在项目目录。

### 2.2 非目标

- 不增加多文件并发下载。
- 不增加下载限速、时间段调度或跨机器同步。
- 不改变现有视频、GIF、圆形视频的媒体筛选规则。
- 不删除已经完成的文件，也不自动清空用户现有的历史队列。
- 不把临时数据或依赖缓存迁移到 C 盘。

## 3. 用户界面与行为

### 3.1 群组/频道页

现有列表扩展为以下列：

| 列 | 含义 |
| --- | --- |
| 监听 | 是否把该群组或频道加入目标白名单 |
| 历史 | 是否扫描并下载该目标的历史视频 |
| 名称 | Telegram 会话名称 |
| 会话 ID | Telegram 会话 ID |

行为规则：

- 只有已启用监听的目标才能开启历史下载。
- 取消监听时保留数据库中的任务和扫描游标，但从配置中移除该目标；以后重新选择时按新目标规则默认关闭历史下载。
- 对新发现且首次选择的目标，“监听”开启、“历史”默认关闭。
- 对升级前已经存在于 `config.toml` 的目标，缺少历史字段时按开启处理，避免静默暂停现有 788 个任务。
- 保存后由现有配置热更新机制在最多 5 秒内生效，不要求重启后台。
- 如果用户关闭当前正在下载任务所属目标的历史开关，当前文件继续完成；完成后不再领取该目标的其他历史任务。

### 3.2 运行页

运行页新增或调整以下信息：

- 当前文件。
- 已下载 / 总大小。
- 完成百分比。
- 当前任务平均速度。
- 实时/补抓等待。
- 可执行的历史等待。
- 已暂停的历史任务。
- 重试等待、已完成、永久失败。

目标状态文本区使用以下状态：

- `监听新内容；历史下载开启`
- `监听新内容；历史下载已暂停`
- `历史扫描完成`
- `历史扫描暂停`
- `访问错误：<已脱敏错误>`

## 4. 配置与兼容性

每个目标在 `config.toml` 中显式保存历史策略：

```toml
[[groups]]
chat_id = -1001234567890
title = "示例频道"
download_history = false
```

兼容规则：

- 读取旧配置时，缺少 `download_history` 的已配置目标按 `true` 处理。
- GUI 新发现的目标在首次选择时按 `false` 处理。
- 下一次保存配置后，所有目标都写出明确布尔值，不再依赖隐式默认。
- 非布尔值视为配置错误，并通过现有配置错误通道显示；后台继续使用上一份有效配置。

`GroupTarget` 增加历史策略字段。Telegram 会话发现结果使用新目标默认值，配置加载器负责旧配置兼容值，两者不混用隐式判断。

## 5. 状态数据库与队列语义

### 5.1 群组状态

`groups` 表增加 `download_history INTEGER NOT NULL DEFAULT 1`。启动时检查表结构并执行幂等迁移，确保现有数据库无需重建。

配置同步时同时更新：

- `enabled`：是否监听该目标。
- `download_history`：是否扫描和领取该目标的历史任务。

### 5.2 历史暂停

不增加新的任务状态。历史暂停由任务来源与群组策略共同派生：

- `source = 'history'` 且目标 `download_history = 0`：任务保留，但不可领取。
- `source IN ('live', 'catchup')`：不受历史策略影响。
- 已经处于 `downloading` 的任务不会被中途取消。

`claim_next` 在数据库查询层排除暂停的历史任务，避免工作线程领取后再退回。

历史扫描器在目标暂停时不继续向更早消息推进，但保留 `history_cursor_id` 和 `history_complete`。重新开启后从原游标继续。

### 5.3 计数

状态统计新增 `paused_history`，并避免重复计数：

- `pending_history`：当前允许领取的历史任务。
- `paused_history`：暂停目标下处于待处理或重试等待的历史任务。
- `retry_wait`：当前未被历史策略暂停的重试任务。

## 6. 可续传下载数据流

固定块大小使用 512 KiB。下载流程如下：

1. 工作线程领取任务并计算最终路径与稳定的 `.part` 路径。
2. 如果最终文件大小与 Telegram 元数据一致，直接标记完成。
3. 检查 `.part`：
   - 大于预期大小：判定损坏，删除并从 0 开始。
   - 等于预期大小：执行最终大小验证并原子移动。
   - 小于预期大小但未对齐 512 KiB：截断到前一个完整块。
   - 合法且已对齐：从现有字节偏移继续。
4. Telegram 网关获取原消息并使用 `iter_download` 从给定偏移读取数据块。
5. 数据块以无额外用户态缓冲的方式追加到项目 `.tmp` 下的 `.part`。
6. 每个数据块更新内存进度；每 8 MiB 或 5 秒执行一次刷新与 `fsync`，取先到条件。
7. 完成后校验文件大小，使用 `os.replace` 原子移动到 `downloads`。
8. 数据库标记完成并清空当前进度。

磁盘空间检查基于“剩余字节 + 512 MiB 安全余量”，而不是再次要求整个文件大小。

## 7. 进度、停滞与停止

工作线程维护以下只读快照：

- 文件名。
- 已下载字节。
- 总字节。
- 百分比。
- 本次任务开始时间。
- 最近一次数据块时间。
- 平均字节/秒。
- 是否从断点恢复。

心跳每 5 秒写入项目 `.runtime/heartbeat.json`。GUI 只读取心跳，不直接读取正在写入的文件。

下载任务与监控循环并行等待：

- 首个数据块或后续数据块连续 120 秒没有进度：取消 Telegram 下载任务，保留已刷新断点并标记瞬时错误。
- 收到停止事件：立即取消 Telegram 下载任务，刷新并关闭 `.part`，把数据库任务恢复为可再次领取状态，然后退出。
- 下载正常完成：取消监控等待并执行最终验证。

重试延迟保持现有策略：5、15、30、60、120 秒，之后每 15 分钟重试。

## 8. 性能依赖

`pyproject.toml` 增加受控范围的 `cryptg` 依赖。项目启动脚本继续通过项目 `.venv` 安装依赖，并把 pip 缓存限制在项目 `.cache/pip`。

验收时确认：

- `cryptg` 可从项目虚拟环境导入。
- Windows CPython 3.12 使用预编译 wheel，不需要本机编译工具链。
- Telethon 自动选择本地 AES-IGE 实现。

仍保持单文件顺序下载，以控制内存、磁盘随机写入和 Telegram 请求压力。

## 9. 错误处理

| 情况 | 处理 |
| --- | --- |
| 网络错误或停滞 | 保留合法 `.part`，进入瞬时重试 |
| 后台停止或进程中断 | 刷新并保留断点，下次启动恢复 |
| `.part` 大于预期大小 | 删除该临时文件并从 0 重试 |
| `.part` 未块对齐 | 截断到上一个完整块后续传 |
| 下载结束但大小不一致 | 保留可验证的完整块并进入重试 |
| 消息删除或媒体永久无效 | 标记永久失败并删除对应 `.part` |
| 登录失效 | 切换为 `needs_login`，不破坏队列和断点 |
| 群组或频道无权限 | 保存访问错误并延迟重试 |
| 磁盘空间不足 | 暂停领取并在 GUI 显示原因 |
| 配置热更新无效 | 保留上一份有效配置并显示配置错误 |

日志不得记录 API Hash、手机号、登录二维码、二步验证密码或会话密钥。

## 10. 测试与验收

### 10.1 自动化测试

- 配置：新字段读写、旧配置默认开启、错误类型验证。
- GUI：监听列与历史列独立切换，新目标或重新选择的目标默认关闭历史，旧配置中的现有目标默认开启。
- 数据库迁移：旧 `groups` 表幂等增加字段，不丢失群组、任务或游标。
- 领取顺序：暂停历史不可领取，实时/补抓仍可领取，重新开启后历史恢复。
- 扫描器：暂停时游标不推进，重新开启后从原游标继续。
- 运行中切换：已经下载中的历史任务允许完成，后续历史任务暂停。
- 断点续传：合法偏移续传、未对齐截断、超大临时文件重置、最终原子移动。
- 进度：字节、总量、百分比、速度和恢复标志进入心跳与 GUI。
- 停滞：120 秒无数据触发取消和重试，期间有进度则不误判。
- 停止：取消下载、刷新断点、服务及时退出。
- 错误分类与日志脱敏保持现有行为。
- 完整现有测试集继续通过。

### 10.2 真实环境验收

使用项目内已有 Telegram 登录会话和用户已选择目标验证：

1. 项目虚拟环境可导入 `cryptg`。
2. 启动后台后无需再次登录。
3. `.part` 在项目 `.tmp` 中出现并持续增长。
4. GUI 每 5 秒内显示字节、百分比和速度变化。
5. 暂停目标历史后，当前文件完成，随后历史等待转为暂停。
6. 新消息任务仍能优先下载。
7. 重启后台后从已有 `.part` 继续，而不是从 0 开始。
8. 至少一个真实视频完成并原子移动到项目 `downloads`。
9. GitHub 与魔塔发布提交一致。

## 11. 交付与回滚
