# v0.3.4 后台共享 Telegram 检索通道设计

## 背景与根因

v0.3.3 已避免配置器启动时为了恢复登录状态而重复打开 Telethon 会话，但“视频检索”仍会在配置器进程中创建临时 `TelethonGateway`。后台下载器同时持有自己的 `TelethonGateway`，两者都使用 `.runtime/telegram.session`。Telethon 的会话文件是 SQLite 数据库并采用 `DELETE` 日志模式；两个进程并发更新会话状态时会触发 `database is locked`。

实机只读证据显示：错误发生时下载器锁与监督器锁均有效，心跳为 `running`，`telegram.session` 的修改时间与检索失败时间一致；会话数据库和应用状态数据库的 `quick_check` 均为 `ok`，因此问题是并发访问而非数据库损坏。应用状态库 `.runtime/state.sqlite3` 已使用 WAL，且失败时没有对应写入活动。

## 目标

- 后台运行时，视频检索复用后台已经连接的 Telegram 客户端。
- 后台停止时，保留配置器临时直连的现有体验。
- 从进程边界上保证同一时刻只有一个客户端打开 `telegram.session`。
- 检索不停止、暂停或重启当前下载，不抢占正在处理的文件。
- 保留现有日期、关键词、数量、选择、取消和入队语义。
- 关键词、说明、文件名和结果列表只存在于内存，不写入 IPC 配置、心跳或日志。
- 不新增第三方依赖、进程、线程或空闲轮询。

## 非目标

- 本次不把登录、退出账号、群组刷新或在线自检全部改造成远程调用。
- 本次不创建第二份 Telegram 授权会话，不复制或迁移现有会话数据库。
- 本次不改变下载优先级、SQLite 队列结构、文件保存位置或断点规则。
- 本次不增加缩略图、本地检索索引、检索历史或自动周期检索。
- 本次不在用户未明确要求时合并或发布候选版。

## 方案选择

采用绑定到 `127.0.0.1` 随机端口的 asyncio 请求通道。

未选择请求/结果文件，因为它会让关键词和结果短暂落盘，并需要轮询。未选择独立检索会话，因为它会增加授权状态、连接和会话维护成本，且仍可能产生 Telegram 会话状态冲突。本机回环通道没有空闲轮询，数据只在内存中传递，并能通过连接生命周期表达取消操作。

## 组件边界

### `search_ipc.py`

新增一个独立模块，包含以下职责：

- `SearchEndpoint`：固定字段的端点元数据模型。
- `SearchRequest` 与 `SearchResponse`：严格校验的协议模型和 JSON 编解码。
- `SearchIpcServer`：在后台事件循环中接受并执行检索请求。
- `SearchIpcClient`：配置器使用的单请求客户端。
- `SearchChannelError`：面向界面的稳定错误，不暴露令牌或内部连接细节。

该模块不依赖 Tk、配置器控制器或下载工作器。服务端通过构造参数接收检索回调、目标校验回调和取消所需的协程；客户端只依赖 `ProjectPaths` 和 asyncio 流。

### 项目路径

`ProjectPaths` 增加：

- `.runtime/search-endpoint.json`：端点元数据。
- `.runtime/telegram-client.lock`：Telegram 会话所有权字节锁。

端点文件固定包含 `schema_version`、`host`、`port`、`token`、`pid` 和 `started_at`。`host` 必须严格等于 `127.0.0.1`，端口由操作系统随机分配，令牌由 `secrets.token_urlsafe(32)` 生成。端点文件不包含任何搜索条件或结果。

客户端只接受这些固定字段。存在新鲜 `running` 心跳时，端点 PID 必须与心跳 PID 一致；不一致即视为陈旧端点。最终仍以成功连接并通过随机令牌验证作为服务身份确认。

### Telegram 会话所有权

当前 `TelethonGateway.__init__()` 会立刻构造 `TelegramClient`，而 Telethon 在构造文件会话时已经可能打开 SQLite。实现必须改为延迟创建：构造函数只保存路径、凭据、客户端工厂和连接选项；`connect()` 先获取 `telegram-client.lock`，成功后才调用客户端工厂并连接。锁持有到 `disconnect()` 完成。客户端创建或连接失败时立即释放；断开失败时也在 `finally` 中释放。重复连接或断开保持幂等。

无法获取锁时抛出明确的会话占用错误，不调用 Telethon，也不打开 SQLite。这样即使后台启动和配置器直连发生竞态，也不会再落入 SQLite 的 `database is locked`。

该保护自动覆盖所有真实 `TelethonGateway` 使用者。后台 IPC 检索调用的是已经连接的网关，不会再次获取锁。

## 服务生命周期

后台完成以下步骤后才发布 `running` 心跳：

1. 获取下载器单实例锁。
2. 创建并连接持有会话所有权锁的 Telegram 网关。
3. 验证授权并启动现有扫描协调器。
4. 启动 `SearchIpcServer`，原子写入端点文件。
5. 写入首个 `running` 心跳并启动现有任务。

IPC 服务使用当前 asyncio 事件循环和 `asyncio.start_server()`，不创建线程或子进程。空闲时没有循环检查，仅由操作系统在新连接到达时唤醒。

后台停止时先关闭监听入口并取消当前检索，再取消下载与扫描任务，最后断开 Telegram。服务删除端点文件前必须重新读取并确认其中令牌仍属于自己，避免旧进程删除新进程端点。进程异常退出后留下的旧文件会在下次启动时原子覆盖。

## 检索路由

`GuiController.search_videos()` 保留现有表单校验，再按以下顺序路由：

1. 如果下载器字节锁有效，必须使用 `SearchIpcClient`；客户端同时核对端点和新鲜心跳的 PID。通道未就绪时返回可重试错误，不允许回退到共享会话。
2. 如果下载器未运行，使用现有临时网关路径。真实网关仍需获取会话所有权锁。
3. 如果直连尝试在竞态中发现会话所有权已被后台获取，只尝试一次 IPC；仍不可用时返回可重试错误，不循环重试。

这保证后台明确停止时检索仍可直接使用；后台正在启动、运行或恢复时则不会打开第二个会话客户端。

## 协议与数据流

连接采用一问一答的 UTF-8 单行 JSON 协议。请求最大 16 KiB，响应最大 1 MiB；超限、字段缺失、额外字段、错误类型、非法日期和非法数量均被拒绝。

请求包含：

- `schema_version`
- `token`
- `operation`，本版仅接受 `search_videos`
- `chat_id`
- `keyword`
- `start_utc` 与 `end_utc`，可为空或带时区 ISO 时间
- `limit`，仅接受 20、50、100

后台再次确认目标仍在当前启用配置内，并限制同一时间最多执行一个手动检索。验证通过后，服务端直接调用现有网关的 `search_videos()`。Telethon 在同一 asyncio 事件循环中复用已有连接；检索只增加用户主动触发的 API 请求，不影响单下载工作器优先级。

服务端使用已经打开的 `StateStore` 查询结果对应的队列状态，并返回现有界面所需的 `SelectableVideo` 字段。最多返回 100 条；说明继续单行化并限制 120 字符。响应不经过磁盘。

客户端收到结果后沿用现有内存模型、选择逻辑和 `enqueue_selected_videos()`。入队仍通过应用状态数据库的现有事务完成。

## 取消语义

客户端发送请求后保持连接打开并等待响应。服务端同时等待检索任务和客户端 EOF：

- 检索先完成：返回结果或脱敏错误，然后关闭连接。
- 用户点击“取消检索”、关闭配置器或切换需要清空检索的生命周期：客户端关闭连接；服务端检测 EOF 后只取消对应检索任务。
- 后台停止：服务端关闭监听并取消当前检索；客户端收到明确的通道关闭错误。

取消不会断开共享 Telegram 网关，不会取消当前视频下载、历史扫描或停机补抓。

## 错误处理

- 后台锁有效但端点不存在：`后台检索通道尚未就绪，请稍后重试`。
- 端点陈旧、端口拒绝或令牌不匹配：`后台检索通道已失效，请稍后重试`。
- 已有检索：`已有检索正在进行，请稍后重试`。
- 后台在检索中退出：`后台已停止，本次检索未完成`。
- Telegram 错误：沿用现有映射并在 GUI 通过 `_safe_error()` 脱敏。
- 会话所有权锁被占用：`Telegram 会话正在由后台使用`，绝不把底层 SQLite 错误展示给用户。

搜索页现有失败路径会清空本次结果、恢复“检索”按钮并允许用户手动重试。设计不增加自动重试、启动网络请求或隐藏回退。

## 安全与隐私

- 监听地址固定为 IPv4 回环地址，不能配置为局域网或公网地址。
- 每次后台启动生成新令牌；服务端先验证协议和令牌，再读取搜索字段。
- 固定字段、类型、长度、数量和响应大小限制防止本机误用造成资源膨胀。
- 端点令牌、关键词、说明、文件名和结果不进入日志或心跳。
- 端点文件属于项目运行目录，其安全边界与现有凭据、会话和进程控制文件一致。令牌用于阻止偶然或无关本机连接，不宣称抵御已获得同一用户文件权限的恶意进程。

## 轻量化预算

- 新增一个仅后台运行期间存在的回环监听 socket。
- 新增一个 asyncio 服务对象；只有用户发起检索时才创建单次处理任务。
- 不新增线程、进程、第三方依赖、定时器、文件轮询或数据库表。
- GUI 继续复用现有 `AsyncBridge` 和检索期间的 100 ms Future 完成检查；空闲时不增加工作。
- 检索并发固定为 1，候选上限继续为 500，返回上限继续为 100。

## 测试策略

### 协议单元测试

- 合法请求和结果往返。
- 非回环地址、错误版本、错误令牌、额外字段、非法日期、非法数量及超限载荷。
- 端点原子写入、令牌匹配删除和陈旧端点替换。

### 会话所有权测试

- 第一个真实网关连接前获取字节锁，断开后释放。
- 构造真实网关不会调用客户端工厂，也不会打开会话；第一次 `connect()` 才在持锁状态下创建客户端。
- 连接失败和断开失败均释放锁。
- 第二个网关在 Telethon 客户端启动前得到明确占用错误。
- Windows 子进程验证进程退出后锁自动恢复。

### 回环集成测试

- 使用临时项目和假网关启动真实 `asyncio.start_server()`。
- 后台路径只调用同一个假网关，GUI 网关工厂调用次数为 0。
- 后台停止路径继续创建、授权、检索并断开临时网关。
- 客户端取消触发服务端任务取消，共享网关保持连接。
- 并发第二次检索、错误令牌、陈旧端点、启动间隙、服务端异常和中途关闭返回预期错误。
- 队列状态随结果返回，下载选中项继续进入现有队列。

### 回归与边界测试

- 完整运行 `scripts/check.ps1`，覆盖登录恢复、群组、检索、队列、下载、托盘、自检和在线更新。
- 搜索日志捕获不包含唯一关键词、说明、文件名或端点令牌。
- 依赖清单不增长；源码中没有新增线程、子进程、空闲 `after()` 或文件轮询。
- 900×720 搜索页布局不变，不新增常驻 UI 控件。
- 合成服务运行时心跳持续推进，下载任务可与检索并行完成。

## 实机与发布边界

本次版本为 v0.3.4 候选。实施和自动化全部在隔离 worktree 中进行，不停止当前真实后台，也不使用真实 Telegram 会话做并发复现。

候选完成后先交付代码、自动化证据和分支选择。只有用户明确要求合并和发布时，才在合并后的 `master` 重新运行 bootstrap、依赖检查和完整测试，向 GitHub 与魔塔发布相同的带说明 `v0.3.4` 标签，并通过受控重启让真实后台加载新代码。重启前后必须验证断点、队列、下载目录和心跳连续性。

## 验收标准

- 后台运行时检索成功且 GUI 不创建第二个 Telegram 网关。
- 后台停止时检索仍可临时直连。
- 取消检索不影响共享网关和下载任务。
- 所有会话客户端都受 `telegram-client.lock` 保护，不再出现 SQLite `database is locked`。
- 检索数据只在内存中传递，运行文件与日志不包含检索内容。
- 没有新增依赖、线程、进程或空闲轮询。
- 完整自动化通过，真实后台在候选开发期间持续运行。
