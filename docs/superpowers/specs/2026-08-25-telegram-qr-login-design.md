# Telegram 二维码登录设计

## 背景与目标

现有 Telegram 视频自动下载器只提供手机号、验证码和二步验证密码登录。该流程可用，但首次配置步骤较多。下一版把 Telegram 官方二维码登录设为账号页主入口，同时保留手机号验证码作为备用方式，并继续复用项目内的 Telethon 会话。

成功标准：

- 账号页以内嵌二维码作为默认登录方式，二维码过期后自动刷新。
- API ID、API Hash 继续必填；二维码登录时手机号可以为空。
- 已有有效会话直接复用，不要求再次扫码。
- 扫码后如 Telegram 要求二步验证，只临时收集密码并完成登录。
- 手机号验证码登录保留在默认折叠的备用区域。
- 二维码令牌、验证码和密码不落盘、不进入日志，二维码不生成图片文件。
- 会话、配置、日志、诊断和下载数据继续只写入项目目录，不使用系统临时目录或 C 盘项目数据目录。
- 下载白名单、历史扫描、实时监听、断线补抓和 24 小时后台运行行为不受改动。

## 方案选择

### 方案 A：账号页内嵌二维码（采用）

在现有账号页显示二维码、有效期和登录状态。二维码过期时原位刷新，手机号流程折叠为备用入口。状态集中、操作直观，也不需要管理额外窗口。

### 方案 B：二维码弹窗

账号页更简洁，但弹窗关闭、异步等待、取消和二维码刷新需要额外生命周期管理，且状态信息容易与主页面割裂，因此不采用。

### 方案 C：保存二维码图片或交给外部程序打开

实现较简单，但会产生额外文件或依赖外部程序，增加隐私和路径控制风险，不符合轻量化及项目内数据隔离要求，因此不采用。

## 登录流程

### 1. 会话优先

用户填写 API ID 和 API Hash 后点击“扫码登录”。控制器先使用项目内现有会话连接 Telegram：

- 会话仍有效时直接返回登录成功，隐藏二维码。
- 会话不存在、未授权或已失效时，进入二维码登录。
- API ID 或 API Hash 无效时停止流程并给出可操作提示。

### 2. 创建和显示二维码

网关通过 Telethon 的二维码登录能力取得一次性 URL 和过期时间。GUI 使用轻量级纯 Python 二维码编码库取得矩阵，并在 Tkinter `Canvas` 中直接绘制黑白方块。二维码只存在于内存和界面中，不保存 PNG、缓存文件或系统临时文件。

GUI 在异步桥中等待 Telegram 授权，主线程只负责绘制和状态更新，窗口在等待期间保持响应。

### 3. 过期和刷新

一次二维码通常只有较短有效期。等待结果分为成功、需要二步验证、已过期、已取消和失败：

- 已过期是正常状态，不弹错误窗口；控制器刷新令牌，GUI 原位重绘并再次等待。
- 用户也可以点击“重新生成”立即替换当前二维码。
- 用户点击“取消登录”或关闭程序时，取消等待任务、断开临时网关并清空二维码。
- 使用登录代次标识忽略旧异步任务的迟到回调，避免取消或刷新后旧结果覆盖新状态。

### 4. 二步验证

如果扫码确认后 Telethon 返回二步验证要求，二维码区域切换为密码输入状态。密码为空时不提交；错误时保留输入区允许重试；成功后立即清空控件及内存引用。密码不写入配置、日志、心跳或诊断报告。

### 5. 手机号备用登录

“使用手机号验证码登录”区域默认折叠。展开后沿用现有发送验证码和完成登录流程。手机号只在该流程中要求非空；二维码登录及后续会话复用不依赖手机号。

## 组件设计

### 1. 凭据模型与配置兼容

`Credentials` 保留 `api_id`、`api_hash` 和 `phone` 字段，将 `phone` 默认设为空字符串。校验拆分为：

- API 基础校验：API ID 大于零且 API Hash 非空，适用于创建网关、二维码登录、会话复用、列群和后台服务。
- 手机登录校验：在基础校验上额外要求手机号非空，只由发送验证码流程调用。

现有包含手机号的 `.runtime/credentials.toml` 保持兼容；二维码用户可以保存空手机号。加载配置时缺少 `phone` 字段也按空字符串处理，避免旧文件或手工配置因该字段缺失而失败。配置存储位置和格式不新增外部文件。

### 2. 网关接口

新增领域对象 `QrLoginChallenge`，只包含二维码 URL 和过期时间。`TelegramGateway` 增加与具体 Telethon 类型隔离的能力：

- 创建二维码挑战。
- 等待当前挑战完成。
- 刷新挑战。
- 提交扫码后的二步验证密码。

`TelethonGateway` 在内部保存当前 Telethon QR 登录对象和二步验证状态。断开连接时清理该状态。二维码过期、二步验证要求、限流和网络错误映射为项目自己的异常，GUI 不直接依赖 Telethon 异常类型。

### 3. GUI 控制器

`GuiController` 继续持有唯一的临时登录网关，并新增二维码登录生命周期方法：

- 启动二维码登录并返回挑战。
- 等待扫码结果。
- 刷新二维码挑战。
- 提交二维码登录的二步验证密码。
- 取消并释放当前登录。

开始任一登录方式前先关闭已有临时登录连接，保证同一时间最多存在一个登录流程。登录成功、取消、不可恢复错误和 GUI 关闭时都执行统一清理；正常二维码过期不会丢弃仍可复用的网关。

### 4. GUI 页面

账号页从上到下分为：

1. API 配置区：API ID、API Hash。
2. 登录状态区：未登录、生成中、等待扫码、等待二步验证、网络恢复中、已登录和失败。
3. 二维码区：二维码、剩余有效时间、“重新生成”和“取消登录”。
4. 二步验证区：仅在扫码后被要求时显示。
5. 手机号备用区：默认折叠，包含手机号、验证码、密码及现有按钮。

登录成功后二维码和密码区隐藏，显示已登录状态及退出当前账号操作。退出动作只注销或清理项目内会话，不触碰下载文件和群组白名单。

### 5. 二维码渲染依赖

增加不带图像扩展的轻量级 `qrcode` 依赖，只使用其矩阵编码能力。Tkinter 自行绘制矩阵，因此不引入 Pillow，也不创建二维码图片文件。依赖继续安装在项目内 `.venv`，启动脚本保持项目内临时目录和缓存环境设置。

## 状态与错误处理

- 二维码正常过期：静默刷新，不计为错误。
- 短暂网络错误：显示“等待网络恢复”，按递增间隔重试，间隔上限 30 秒；用户可随时取消。
- Telegram 限流：优先遵守服务器返回的等待时长，不提前重试。
- API 配置错误：停止自动重试，提示检查 API ID 和 API Hash。
- 二步验证密码错误：保持当前登录流程并允许重新输入。
- 会话注销或撤销：关闭失效连接并回到可重新扫码状态。
- 同时触发多个按钮：禁用冲突操作，并通过控制器单登录约束拒绝重复任务。
- 程序关闭：先取消登录 Future，再断开网关，最后关闭异步桥。

日志脱敏覆盖 API Hash、二维码 URL/令牌、手机号、验证码和二步验证密码。脱敏器只登记非空敏感值，防止空手机号参与字符串替换；二维码 URL 不传入通用异常文本或日志。异常展示只保留问题类别和用户可执行建议，不输出 Telethon 请求对象或会话内容。

## 自检扩展

现有一键自检增加以下检查：

- `qrcode` 包可导入并能生成二维码矩阵。
- `.runtime` 和会话父目录位于项目内且可写。
- GUI 控制器是否存在已结束但尚未清理的登录任务。
- 存在凭据时，API 基础字段是否有效；手机号为空不再误报。
- 在线检查可连接现有会话并判断授权状态；未授权提示需要扫码或备用登录。

自检不创建二维码、不发送验证码、不触发登录，也不读取或输出会话内容。诊断报告继续原子保存到项目内 `logs/diagnostics/` 并执行现有脱敏。

## 测试策略

按测试驱动开发实施，并保持既有测试全部通过：

- 模型与配置测试：无手机号的 API 凭据有效；手机号流程仍要求手机号；旧凭据文件兼容；缺失 `phone` 字段按空值读取。
- 网关测试：创建、刷新、成功扫码、正常过期、取消、二步验证和密码错误。
- 控制器测试：会话优先、同一时间单登录、自动刷新所需状态、手动刷新、迟到回调隔离和统一清理。
- GUI 测试：二维码矩阵渲染、状态切换、备用区折叠、按钮互斥、倒计时和关闭窗口。
- 错误测试：网络退避、Telegram 限流、无效 API、失效会话、空敏感值和敏感信息脱敏。
- 自检测试：二维码依赖、项目内可写路径、空手机号、授权状态和残留任务。
- 路径隔离测试：二维码登录全流程不创建图片或系统临时文件，所有持久数据仍位于项目根目录。
- 回归测试：群组白名单、历史与实时下载、补抓、守护、停止和诊断行为不变。

完成后运行完整 `scripts/check.ps1`，并进行一次使用测试账号的人工扫码冒烟测试。人工测试只验证授权、会话复用、二维码过期刷新和取消，不下载未选群组内容。

## 明确不包含

- Telegram Passkey 登录、机器人 Token 登录或多账号管理。
- 取消 API ID、API Hash 要求。
- 把二维码保存为图片、复制到剪贴板或交给浏览器打开。
- 将凭据、二维码或会话上传到外部服务。
- 改变下载群组白名单、下载格式、存储布局或 Windows 后台守护策略。
