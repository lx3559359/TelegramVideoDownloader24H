# 手动在线更新设计

## 背景与目标

项目目前通过 GitHub 和魔塔两个 Git 远程发布，启动器从项目源码进行 editable 安装，但配置器没有版本检查或安全更新入口。本功能增加用户主动触发的一键更新，同时保持长期后台下载期间零更新开销。

本次统一发布版本为 `v0.2.0`。后续更新只识别 `vX.Y.Z` 形式的稳定标签，不跟随开发中的 `master` 提交。

## 更新源与版本规则

- GitHub 为主源：`https://github.com/lx3559359/TelegramVideoDownloader24H.git`。
- GitHub 查询失败时自动切换魔塔：`https://www.modelscope.cn/studios/lx3559359/TelegramVideoDownloader24H.git`。
- 两个远程必须发布指向同一提交的带说明标签。
- 版本比较只接受严格的三段式非负整数语义版本，拒绝预发布文本、畸形标签和降级。
- 远程查询、抓取和安装只在用户手动操作时发生；没有启动检查、定时器或后台轮询。

当前版本来自项目包元数据。检查器使用 `git ls-remote --tags --refs` 获取稳定标签，选出高于当前版本的最新标签；抓取精确标签后验证其提交是当前 `HEAD` 的快进后继。

## 界面与交互

“运行”页增加“软件更新”区域：

- 当前版本。
- “检查更新”按钮。
- 更新源、最新版本和状态摘要。
- 可搜索的变更文件列表，显示增加、修改和删除。
- “安装更新”按钮，仅在全部安全前提满足时启用。

托盘菜单增加“检查更新”。该动作恢复配置器、切换到更新区域并发起一次手动检查。

变更文件列表只用于搜索、筛选和预览。安装始终更新完整标签，不能取消单个程序文件，避免新旧版本混合、Git 工作区变脏和后续快进失败。

## 组件边界

新增独立 `UpdateManager`，负责版本解析、远程查询、源回退、标签抓取、差异预览和安全前提判断。模块采用延迟导入，不进入下载 service。

新增独立更新执行器及 PowerShell 入口，负责在 GUI 退出后更新工作树、安装依赖、验证导入、回滚、重新打开配置器和按原状态恢复下载器。正式修改代码前，把执行器复制到项目 `.tmp` 的单次更新目录并从副本运行，避免更新脚本覆盖自身。更新执行器通过项目内状态文件传递固定字段，不接受任意 shell 命令。

运行数据：

- `.runtime/update-request.json`：目标标签、更新前提交、是否恢复下载器和随机请求标识。
- `.runtime/update-result.json`：成功/失败、最终版本和脱敏摘要。
- `logs/updater.log`：更新阶段和错误日志，不记录凭据、会话或下载文件名。

状态文件均使用临时文件加 `os.replace` 原子写入。

## 检查与安装前提

安装前必须同时满足：

- 当前分支为 `master`。
- `git status --porcelain --untracked-files=all` 为空；Git 已忽略的运行目录不计入。
- 当前提交与检查时记录一致。
- 目标标签高于当前版本且可从当前提交快进。
- 没有正在进行的 Telegram 登录任务。
- 更新执行器、PowerShell、Git 和项目 Python 可用。

任一条件不满足时只显示原因，不停止下载器、不修改代码。

## 安装生命周期

1. 用户检查更新并查看变更文件。
2. 点击安装并确认目标版本、将短暂停止下载及恢复规则。
3. 在 GUI 仍运行时抓取精确标签并完成所有只读验证。
4. 记录更新前提交与下载器是否实际运行。
5. 若下载器运行，使用现有停止请求等待当前 Telegram 调用取消、断点安全落盘和服务退出；超时则取消更新。
6. 原子写入更新请求，把独立更新器复制到项目 `.tmp` 的随机单次目录并从副本启动，然后退出托盘和配置器。
7. 更新器再次验证提交和工作区状态，以 `git merge --ff-only` 切换到目标标签提交。
8. 运行项目 `scripts/bootstrap.ps1`，验证 Python 版本、核心依赖、托盘依赖和包导入。
9. 写入结果并重新启动配置器；更新前下载器处于运行状态时再启动后台，否则保持停止。

更新期间不修改 `.runtime/telegram.session`、配置、SQLite、断点、日志历史、项目 `downloads` 或用户选择的外部下载目录。

## 失败与回滚

- 远程不可达：GitHub 失败后尝试魔塔；两者都失败则保持当前版本。
- 停止超时：在代码更新前终止流程，下载器状态保持真实结果，不强制杀进程。
- 快进或依赖安装失败：只有当 `HEAD` 和工作区仍处于更新器预期状态时才回滚。
- 回滚先把 `master` 引用恢复到更新前提交，再使用 `git restore --source=HEAD --staged --worktree -- .` 恢复受版本控制文件；不使用 `git reset --hard`。
- 回滚后重新运行旧版本 bootstrap，并按更新前状态恢复下载器。
- 如果安全前提不成立，不执行破坏性回滚，只保留日志并显示人工恢复说明。

由于安装前拒绝任何本地修改，回滚只撤销本次更新器产生的版本控制文件变化。被 Git 忽略的数据和用户选择的外部目录永远不进入恢复目标。

## 性能

更新模块不被下载 service 导入。正常长期运行时没有网络请求、轮询、额外进程或更新线程。检查更新和差异搜索只在更新区域打开并由用户点击后运行；窗口关闭后释放相关结果对象。

Git 抓取传输变化对象，避免每次下载完整程序压缩包。变更文件预览不改变安装范围。

## 测试与发布

- 语义版本解析、无更新、新稳定版本、忽略畸形与预发布标签。
- GitHub 成功、GitHub 失败后魔塔成功、双源失败。
- 变更文件搜索与状态显示。
- 脏工作区、非 `master`、提交变化、非快进和登录任务阻止安装。
- 下载器原为运行或停止两种生命周期。
- 停止超时、快进失败、bootstrap 失败、安全回滚和拒绝不安全回滚。
- 状态文件原子写入、日志脱敏和项目数据不被版本恢复触及。
- 托盘动作只恢复更新界面，不在托盘线程运行 Git。
- 完整 pytest、compileall、Windows 脚本边界检查和真实更新冒烟验收。

发布时把包版本更新为 `0.2.0`，快进合并到 `master`，在 GitHub 与魔塔同时推送 `master` 和指向同一提交的带说明 `v0.2.0` 标签。发布后比较两个远程的分支与标签提交，确认完全一致。
