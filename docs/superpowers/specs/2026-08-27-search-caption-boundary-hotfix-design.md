# v0.3.5 检索说明文字边界热修复设计

## 背景

v0.3.4 已让后台运行时的视频检索复用下载器持有的 Telegram 连接，并通过本机回环 IPC 返回结果。发布后的实机验收确认下载断点和 IPC 端点正常，但不带关键词检索 20 条真实结果时，服务返回“说明必须是最多 120 字符的单行文本”。

根因位于 `normalize_search_caption()`：它先把说明中的空白压成单个空格，再截取前 120 个字符。如果第 120 个字符恰好是词间空格，产物会以空格结尾；IPC 编码器再次调用同一规范化规则验证时会去掉该尾部空格，因此把生产者生成的结果误判为未规范化。纯函数复现得到长度 120、末尾为空格且二次规范化不相等，与实机错误一致。

## 目标与边界

- 保证 `normalize_search_caption()` 的产物始终是最多 120 字符、单行、无首尾空白且可重复规范化的文本。
- 保持 IPC 协议版本、字段、响应大小限制和严格接收校验不变。
- 保持现有检索结果展示、关键词、日期、数量和队列状态行为不变。
- 作为不可变的 `v0.3.5` 补丁版本发布，不移动已经公开的 `v0.3.4` 标签。
- 不新增依赖、线程、进程、轮询、持久化文件、数据库字段或日志内容。

## 方案选择

采用源头修复：空白压缩和 120 字符截断后，再去除截断产生的尾部空格。这样生产者直接满足既有协议不变量，GUI 直连检索和后台 IPC 检索获得相同的说明文字。

不采用以下替代方案：

- 不放宽 IPC 接收校验，因为这会允许协议中出现生产者本应消除的不规范文本。
- 不只在服务编码前重新规范化，因为这会掩盖上游函数不具备幂等性，并让直连与后台路径存在不同的数据处理位置。

## 数据流与错误处理

Telegram 原始说明继续由网关传给 `normalize_search_caption()`。函数压缩所有空白、限制为 120 个字符，并移除截断边界上的尾部空格；结果随后进入 `VideoSearchResult`。后台模式经 IPC 严格编码和解码，停止模式继续直接交给 GUI。协议仍拒绝外部构造的多行、超长或其他未规范化说明，不吞掉真实 Telegram、连接或队列错误。

修复不改变搜索端点令牌、PID 校验、取消语义或会话锁。若 IPC 通道尚未就绪或已失效，仍显示现有稳定错误并要求用户手动重试。

## 测试与发布

1. 在选择性下载纯函数测试中加入“第 120 个字符是词间空格”的回归，先确认旧实现产生尾部空格并失败，再确认修复后结果无尾部空格且二次规范化相等。
2. 在 IPC 测试中把该边界说明装入真实 `SelectableVideo`，证明成功响应可以编码、解码并保持一致；现有多行和 121 字符拒绝测试继续通过。
3. 运行选择性下载与 IPC 专项测试，再运行 `pip check` 和完整 `scripts/check.ps1`。
4. 将包版本、发布测试和简短用户说明更新为 v0.3.5，创建带说明标签并同步 GitHub、魔塔的 `master` 与 `v0.3.5`。
5. 受控重启真实后台，确认新 PID、回环端点、`resumed=true` 和下载字节继续增长；随后用合法数量 20 做一次不打印关键词、说明或文件名的实机检索，确认 GUI 控制器走 IPC 且返回结果。
